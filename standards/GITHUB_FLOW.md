# 共通GitHub開発フロー

## 適用原則
個別の明示指示・リポジトリ固有の運用を優先し、指定がなければこの文書を既定値とします。意図せず `develop` や `release` を追加しません。

## 標準: main中心のGitHub Flow
1. 既存Issue（open/closed）、PR、ブランチ、README/docs、実装の状態を確認。
2. 必要ならIssueを作成。ユーザーが「Issueのみ」「実装しない」と指示した場合は厳守。
3. `main` から短命ブランチを切り、変更範囲を絞って実装。
4. Lint、型チェック、関連テスト、ビルドのうち適切なものを実行。
5. PRを `main` に作成し、変更・検証結果・関連Issue・未確認点を明記。
6. 明示的なマージ許可と必要なチェック完了後にマージ。
7. マージ後は必要に応じてIssueを閉じ、作業ブランチを削除。本番反映を確認。

推奨ブランチ名: `feature/123-description`、`fix/124-description`、`refactor/125-description`、`docs/126-description`、`chore/127-description`。Issue番号がない作業もあるため番号は必須ではありません。既存のブランチ命名規則があればそちらを優先します。

## プレビューモード: main + develop
- `develop` が存在し、当該リポジトリが明示的に使用している場合のみ適用。
- 作業ブランチは原則 `develop` から切り、検証PRも `develop` 向けに作成。
- `main` は本番、`develop` はオンラインプレビューとして運用。
- developからmainへの反映は別PR等で管理し、ユーザーのマージ許可に従う。
- developの参考資料や試験的ファイルがmainに混入しないようPR差分を確認。Gitはディレクトリ単位の「自動マージ除外」を標準提供しません。
- 完成済みの小規模リポジトリなどに、理由なくdevelopを追加しません。

## 自動化エージェント向け
- 同種のIssue・PR・作業ブランチを先に検索し、二重作成を防ぐ。
- 他人の変更があるブランチを無断で上書き・force pushしない。
- CI失敗、検証未実施、外部環境依存の未確認点を隠さない。
- PRのマージ・Issueのクローズ・ブランチ削除は、指示された範囲と完了状態に従う。
- ユーザーが「mainへ直接反映してよい」と明示した場合は、保護設定・権限に反しない範囲で例外として扱える。
- マージ済みPRの関連Issueを機械的にすべて閉じない。実際の完了条件を確認する。

## リポジトリ設定による強制
この文書だけではmainへの直接pushを技術的に防止できません。必要に応じて各リポジトリのRulesets/ブランチ保護でPR・CI必須などを設定してください。個人アカウント下のルール一括適用は契約・権限に依存します。
